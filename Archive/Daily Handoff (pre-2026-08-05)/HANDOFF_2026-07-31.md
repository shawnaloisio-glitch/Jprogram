## 1. Project Overview

**Jprogram** is a local Python pipeline that converts Japanese-language source material (podcast transcripts, anime subtitles; future: manga, visual novels, other text) into a structured, analyzable corpus.

The pipeline converts every source into a canonical form, then processes it through a sequence of small, single-purpose, file-based, restartable stages.

**Role of the DeepSeek parser:** the only AI component. It receives one ~10,000-character job of Japanese text and produces a structured JSON annotation of that job (sentences, words, lexical forms, grammar chunks, expressions) while preserving the original text exactly.

**Component roles (must stay separate):**
- **Parser (DeepSeek):** preserves linguistic evidence; adds approved annotation layers. Never computes statistics or conclusions.
- **Response Validator (deterministic):** gates each parser response — structurally valid and evidence-preserving, or rejected. Never repairs.
- **Corpus Builder (deterministic, not yet implemented):** converts validated evidence into the canonical corpus — recomputes unreliable LLM fields, assigns global positions, adds provenance.
- **Analyzer (future, deterministic):** computes all statistics, comparisons, and reports from the corpus. Never re-parses.

**Core principle — "Garbage in, garbage out":** the parser preserves original evidence and adds structured supplemental information. It must not replace source evidence with interpretations. Surface/text are authoritative occurrence evidence; lexical forms and expression patterns are grouping labels only.

## 3. Frozen Design Decisions

These must NOT be casually reopened. Do not reopen without evidence of a genuine contradiction.

- **Exact sentence preservation:** each sentence is the complete original Japanese sentence, preserved exactly (no normalization, no punctuation changes).
- **Surface + lexical preservation:** every word occurrence carries both the exact `surface` and a dictionary/base `lexical` form (食べました → 食べる). Surface is never replaced by lexical. `lexical` is null rather than invented.
- **Longest-complete-expression rule:** record only the longest complete meaningful expression; do not separately record shorter nested expressions (なぜかというと yes; a nested という no). Independent non-overlapping expressions may both be recorded.
- **Word segmentation policy:** whitespace-delimited sources keep their existing whitespace-delimited units verbatim; non-delimited Japanese uses pragmatic reader-perceived units; inflected forms stay intact (食べました, never 食べ/まし/た); no POS.
- **Evidence-layer separation:** sentences, words, grammar chunks, and expressions are separate layers; chunks are a flat non-overlapping partition (a word belongs to at most one chunk); expressions are an overlapping layer.
- **0-based indices** everywhere; **half-open spans** everywhere (start inclusive, end exclusive), matching Python slicing.
- **Job-local parser positions only.** The parser never invents source-global IDs/offsets; the Corpus Builder assigns global ordering/IDs deterministically.
- **Canonical corpus is sentence-per-line JSONL** (named fields), the single source of truth (Rule 5). Analyzers never modify it.
- **Deterministic Builder responsibilities:** the Builder deterministically recomputes fields the LLM is bad at (character spans, chunk text), assigns sections from source markers, assigns global positions/IDs, stamps provenance, and performs the source-reconstruction integrity check.
- **Parser/analyzer separation:** the parser never computes frequency, dispersion, clustering, distances, I+1, reports, or any statistics.
- **Evidence vs grouping labels:** WHAT OCCURRED (exact sentence, surface, expression surface, positions) vs WHAT IT REPRESENTS FOR GROUPING (lexical form, expression pattern).
- **Parser output is exactly ONE valid JSON object** per job (no fences, prose, comments, or JSONL).

## 4. Final Parser Format Decision

The production parser configuration (frozen after TASK 20):

- **model:** `deepseek-v4-flash`
- **thinking:** `{"type": "disabled"}` (non-thinking; direct response, no reasoning tokens)
- **response_format:** `{"type": "json_object"}`
- **max_tokens:** explicit, ≥ 32768 (non-thinking default output cap is 8192; API maximum is 384K)
- **no `reasoning_effort`** (low effort proved unreliable)
- **hybrid fixed-position-array intermediate format**

**Hybrid column definitions** (words/chunks/expressions are positional arrays; sentences remain named objects):

```
{
  "source_name": string,
  "job_number": integer,
  "sentences": [
    {
      "sentence_index": int,        # 0-based, job-local
      "text": string,               # exact original Japanese
      "words":       [ [index, surface, lexical, char_start, char_end], ... ],
      "chunks":      [ [index, text, start_word, end_word], ... ],
      "expressions": [ [index, surface, start_word, end_word, pattern], ... ]
    }
  ]
}
```

- `char_start`/`char_end` are sentence-relative; invariant `text[char_start:char_end] == surface`.
- The Corpus Builder expands this into **named canonical JSONL** (one sentence per record) after validating.

The named-vs-array format decision was made because the hybrid format is substantially more token-efficient and reliably parseable; the canonical corpus stays readable/named.

## 5. Benchmark Results

All benchmarks used the same 1,242-character 折り紙 job and `deepseek-v4-flash`. Raw responses preserved outside the project (not in the pipeline folders).

### TASK 17 — format + thinking-mode benchmark (first controlled run)
- **Named format (A):** `finish_reason=length`, 65,536 completion tokens (44,925 reasoning), truncated → invalid JSON. Could not complete the job.
- **Hybrid format (B):** completed, valid JSON, 35,384 completion tokens (28,053 reasoning) — but dropped one sentence (`できました。`).
- **Hybrid repeat (C):** 65,536 completion tokens, ALL reasoning, zero content.
- **Conclusion:** completion/reasoning failure was separate from schema reliability. The hybrid is cheaper and structurally sound when it completes; the reasoning model was the bottleneck. Named format could not complete even a small job.

### TASK 19 — reasoning-control benchmark (thinking disabled / low effort)
- **Non-thinking + json (A and C):** reasoning eliminated (0 reasoning tokens), but output truncated at exactly 8,192 completion tokens (default non-thinking cap) → incomplete.
- **Low-effort thinking (B):** 65,536 reasoning tokens, zero content — `reasoning_effort: "low"` is unreliable.
- **Findings:** thinking can be disabled (`thinking: {type: "disabled"}`); `max_tokens` must be set explicitly; `response_format: json_object` retained; prompt caching confirmed (static prompt prefix hit ~2,816/2,820 tokens from the second call on).

### TASK 20 — final controlled benchmark (decisive)
Configuration: non-thinking + json_object + `max_tokens=32768` + hybrid format, three identical calls.
- **3/3 `finish_reason=stop`; 3/3 valid JSON; 0 reasoning tokens.** Completion tokens: 16,229 / 17,154 / 16,277.
- **Evidence reconstruction succeeded 3/3** (whitespace-normalized sentence concatenation equals the clean job text).
- **Word surfaces partitioned sentences correctly 3/3** (106/106 sentences; 0 dropped, 0 mis-split; all sentence texts end in 。！？).
- **Recurring problem:** LLM character offsets are unreliable on Japanese — 34–78 char-span mismatches per response (6.6%–15.2% of words). All are validator-detectable; none indicate evidence corruption.
- **Therefore:** ordered word surfaces are authoritative (they exactly partition each sentence), and the **Corpus Builder must deterministically recompute character spans and chunk text** from the surfaces.

**Label discipline:** the token counts and finish reasons above are confirmed measurements. The 8,192 default cap and the ~13 output tokens per source character at production scale are inferences. Everything about recommended configuration is a recommendation (now adopted as frozen).

## 6. Response Validator

**Implemented:** `Data Processor\response_validator.py` (replaced a stale placeholder) plus `Data Processor\response_validator_test.py`.

**What it validates** (one parser response for one job, deterministic, machine-readable result `{valid, errors, warnings, summary}`):
- Top level: valid JSON object; required `source_name` (string), `job_number` (integer), `sentences` (array).
- Sentences: `sentence_index` integer, 0-based, strictly monotonic; non-empty `text`; `words`/`chunks`/`expressions` arrays.
- Words: exactly 5 columns `[index, surface, lexical, char_start, char_end]`; types; monotonic indices; span range checks; `text[char_start:char_end] == surface`.
- **Fatal vs non-fatal span errors:** char-span mismatches are reported as **non-fatal** (the Corpus Builder recomputes them from the authoritative surfaces). Everything else is **fatal** — including the word-surface partition mismatch (evidence corruption).
- **Evidence partition validation:** the ordered word surfaces must reconstruct the sentence's non-whitespace characters in order; this distinguishes span errors from evidence errors.
- **Chunks:** exactly 4 columns; valid spans; no overlap; chunk text compared against the word-span surfaces (not the unreliable char offsets).
- **Expressions:** exactly 5 columns; valid spans; surface-vs-word-span check; overlap allowed; obvious duplicates → warning only.
- **Identity validation:** parser `source_name`/`job_number` compared against request metadata; mismatch is non-fatal (request metadata authoritative).

**It never repairs data** — it only validates and reports.

**Test result: 20 tests passed, 0 failed.** Includes a real benchmark response demonstrating 78 span errors detected while evidence integrity (partition) was preserved.

## 15. Analyzer Design Principles

These principles govern Analyzer architecture work. The Analyzer has not been implemented; nothing here is code.

### Analyzer Purpose

The Analyzer is a **deterministic corpus transformation layer**.

It does NOT produce:
- conclusions
- recommendations
- learning advice
- interpretations

It produces **alternate mechanical views of the canonical corpus**. Analyzer output is **data products** consumed by later interpretation layers.

Architecture:

```
Canonical Corpus
        |
        ↓
Analyzer Utilities
        |
        ↓
Structured Data Outputs
        |
        ↓
Lesson Coach / Human Interpretation
```

### Analyzer Design Rule

**One script per job/function.**

Each utility:
- reads canonical JSONL
- performs deterministic calculations
- writes structured output
- has independent tests

**No utility contains recommendation logic.**

### Required Analyzer Utility Categories

1. **Frequency Analysis**
   Measures: occurrence counts, sentence counts, source counts, section counts.
   **Important:** frequency alone is insufficient.

2. **Distribution Analysis (required core feature)**
   The Analyzer must measure **exposure distribution**, not only totals.
   Required concepts:
   - occurrence spacing
   - average distance between occurrences
   - median distance
   - maximum gap
   - minimum gap
   - spread across lessons/sources
   - corpus coverage
   - clustering vs distribution patterns

   Reason: a word appearing 50 times in one lesson is different data from a word appearing once across 50 lessons.

3. **Grammar Pattern Analysis**
   Mechanical measurements only: frequency, distribution, first occurrence, recurrence, source coverage.
   **No importance ranking.**

4. **Expression/Chunk Analysis**
   Measures: expression frequency, distribution, recurrence, context locations.

5. **Vocabulary Exposure Analysis**
   Supports: exposure counts, first appearance, repeated encounters, distribution characteristics.
   The Analyzer **reports exposure patterns**; it does **not** decide acquisition or learning priority.

6. **Corpus/Sentence Metrics**
   Potential mechanical views: sentence length, word count, chunk count, expression density, kanji density, source statistics.
   **No subjective difficulty scores** unless explicitly defined later.

### Frozen Principle

**Frequency without distribution is incomplete data.**

The Analyzer must measure both:
- how often something occurs
- how that exposure is distributed through the corpus

## 23. Source Integrity Principle

Every imported source receives:
- a stable human-readable source_id
- a SHA-256 hash fingerprint of the original source file
- metadata describing source type and processing requirements
- lineage information connecting derived artifacts back to the original source

Design rules:

1. **Hashes are audit identifiers, not primary IDs.** source_id remains human-readable and organizational; SHA-256 is used to detect duplicates, corruption, and changes.
2. **Source files are treated as immutable inputs.** Cleaning and parsing create derived artifacts; corpus JSONL is rebuildable from earlier stages.
3. **Each processing stage should preserve traceability:** Raw Source → Cleaner + cleaner version → Parser + parser version → Validator → Canonical Corpus.
4. **Metadata should eventually include:** original filename, source type, format, language, SHA-256 hash, cleaner version, parser version, validator version, and derived artifact hashes.
5. **This system is designed for rebuildability.** The source file remains the source of truth; cleaned files and corpus files are derived products; future database/index systems are derived views, not replacements for provenance.

Recorded as an approved/frozen design decision. No implementation yet.

## 24. Source Intake Architecture

Approved / frozen design (no implementation yet).

- **Source Intake Manager boundary:** registers incoming files, creates source_id, calculates SHA-256, stores registry metadata, selects cleaning_profile, and routes to the correct cleaner.
- **Cleaner boundary:** cleaners only clean content; they do not create source identity, manage hashes, or manage registry metadata.
- **source_type vs cleaning_profile:** separate concepts (e.g., source_type=anime_subtitle, cleaning_profile=subtitle_standard_v1); cleaning profiles are versioned and extensible.
- **Source Registry purpose:** the authoritative per-source metadata store (identity, classification, processing, lineage, lifecycle_status); one JSON file per source_id.
- **Naming convention:** `{type}_{slug}_{sequence}` (e.g., sub_sousou-no-frieren_ep001, pod_conteppei_ep051, manga_one-piece_ch012).
- **lifecycle_status concept:** registered -> cleaning -> cleaned -> processing -> parsed -> validated -> corpus_created -> complete, with failure states (failed_*).
- **Possible future evolution:** separation of processing history (per-stage records) from the source record.
