# AI Coding Environment — Design Spec (Draft)

Status: **DRAFT — in progress.** This is a living document, not a final spec. Update it as decisions get made; don't treat anything here as frozen until explicitly marked settled.

---

## 1. Purpose

Redesign the human/AI operating structure for Jprogram development (and future projects, e.g. the planned Chinese-corpus project), replacing the OpenAI-desktop-as-Advisor setup that led to context degradation and an incomplete handoff-package workflow.

Project goals this structure serves (unchanged from original protocol):
1. Build the best possible language corpus program — no compromises.
2. Make the final program as token-efficient as possible.
3. Learn to manage an AI coding environment effectively.
4. This work is separate from, and does not interfere with, actual Japanese study.

---

## 2. Roles (carried over from original Owner/Advisor/Coder/Auditor protocol)

- **Owner** — Shawn. Product goals, priorities, tradeoffs, architectural approval. Final decision authority.
- **Advisor** — translation/evaluation layer. Does not decide, does not implement. Identifies risk, challenges unsupported assumptions, preserves architectural integrity.
- **Coder** — implementation. Currently OpenCode + DeepSeek ("OC").
- **Auditor** — independent review, invoked when Advisor's confidence is Moderate/Low or the change affects core spec/structure. Historically Qwen; used once in ~60 hours of development, and per `TODO.md`, was still listed as a **pending** review, not confirmed complete.

**Known gap from prior setup:** Advisor was supposed to own the decision of when to invoke Auditor, but OpenAI-as-Advisor failed to exercise that authority in practice. This is being treated as a carried-forward rule with a fixed execution gap, not a rule up for re-decision.

## 3. Candidate new structure (under evaluation, NOT yet finalized)

- **Advisor** → migrating from OpenAI-desktop to **Claude Code (CC)** on a $20/mo Pro plan, used in a deliberately restrained "evaluate and advise, don't auto-implement" mode.
- **Coder** → stays OpenCode + DeepSeek ("OC") — cheap, currently working, keeps token-heavy implementation off the Anthropic pool.
- **Auditor** → candidate: a second, ad hoc CC session, spun up during a guaranteed ~5-hour daily study window (dead capacity otherwise), given real repo/test access (fixing a flaw in the old Qwen setup, which reportedly only ever saw OC's own narrated output, not raw diffs/tests).
- This chat (Claude.ai, free tier) → already functioning as a no-cost, git-aware conversational layer; role going forward TBD (see open questions).

## 4. Settled / working decisions

- **Data-source hierarchy for any evaluator (Advisor or Auditor):** raw `git diff`/`git status`, test output/exit codes, and raw file contents are primary evidence. An agent's own narrative summary of its work is secondary — useful for orientation and speed, but treated as a claim to verify, never as evidence itself. (Directly motivated by the API-key incident, where OC's self-classification of its own fix glossed over the actual open question.)
- **Existing OC reporting contract is already documented** in `TODO.md` §11 ("OC Operating Instructions"): TASK number, files changed / not changed, tests performed, boundary confirmation, ending in `STOPPED.` or `Continue to next section?`. Any new capture mechanism should parse/consume this existing format rather than invent a new one.
- **Terminology collision flagged:** `Production Manager` is already a real, built software component in the codebase (`Production Manager/production_manager.py`) — it launches pipeline stage subprocesses, handles queue/resume, and monitoring. This is distinct from any workflow role Shawn might describe informally as "production manager for OC." A different term is needed for the OC-orchestration workflow role to avoid confusion with the existing code component.
- **Approval checkpoint must stay manual, at minimum in the Owner-to-OC direction**, even as Advisor-to-OC output capture gets automated. Automatic capture of OC's output by CC is fine (removes copy/paste friction on that leg); auto-sending CC's resulting package back to OC without Shawn relaying it would remove the human approval gate the whole protocol depends on, and is explicitly NOT the intent right now.
- **Session hygiene (git as persistent state, scoped/bounded sessions) is the actual fix for the original context-degradation problem** — not simply which model plays Advisor. This discipline should carry forward regardless of tooling.
- **Multiple concurrent CC sessions share ONE Pro usage pool** — running sessions in parallel does not multiply capacity, it spreads the same budget across more concurrent work.
- **Auditor trigger authority and cadence (resolves prior 60-hour/OAI failure to invoke):** Owner retains final authority to spin up Auditor — Advisor-CC does not get to decide and silently skip it, which is the failure mode that happened with OAI. Every Advisor-CC report must include a mandatory, structured trigger field (`Audit trigger: Yes/No — confidence: High/Moderate/Low, reason: ___`), piggybacked on the diff/output read Advisor is already doing each cycle — not a separate deep-scan routine. Part of the trigger check is deterministic and free: if OC's diff touches any file listed under the frozen components in `TODO.md` §4 (parser, validator, builder, canonical format, analysis, transport), trigger = Yes automatically, no judgment call needed. Judgment-based (Moderate/Low confidence) evaluation is reserved for changes outside the frozen list. Actual Auditor sessions, when triggered, are batched into the existing guaranteed ~5-hour daily study window rather than spun up ad hoc mid-session. **Logging:** every trigger-field decision (Yes or No) gets recorded persistently in its own dedicated folder (e.g. `Audit Log/`, separate from `Audits/` which holds actual audit reports), not just left inside an ephemeral session report — giving a queryable history of trigger decisions over time to check whether the invocation rate/conditions are calibrated correctly.
- **Permission model: Advisor and Auditor, not a third role.** Advisor-CC is **read-only, no write access** — structural, not just instructional, so it can't drift into auto-fixing what it's supposed to only evaluate. Auditor gets **read + execute by default** (can run the existing test suite / existing scripts as-is — this alone covers most "run a test file" needs, since executing existing tests doesn't require write access to tracked source). **Write access for Auditor is off by default and is never self-granted mid-session** — if Auditor determines it needs write access to investigate further (e.g. modifying a fixture to test a hypothesis), it must stop and explicitly request it from Owner, who grants it temporarily for that specific investigation. This was chosen over a self-judged "scratch/investigative vs. real fix" tiered-write model and over adding a third "Tester" role, because both alternatives still required the AI to classify its own actions in the moment — the same self-grading failure shape as the API-key incident and the bootstrap-doc handoff failure. Making the write toggle an explicit Owner-granted state, not an AI judgment call, removes that drift risk.
  - **Concrete mechanism (confirmed via Anthropic's own docs):** Claude Code has a built-in, tool-enforced **Plan mode** (`Shift+Tab` twice, or `claude --permission-mode plan`) — CC can read, search, explore, and run read-only commands, but cannot write, edit, or run state-changing commands until a human explicitly approves and exits the mode. This is enforced at the tool level, not by instruction/memory. **Advisor-CC runs in Plan mode as standing default**, which also resolves the separate "autonomy scope" question — Plan mode structurally prevents auto-fixing, no discretionary instruction needed. Auditor-CC runs in normal ask-first mode as default (prompts for approval before any write or side-effecting command) — already matches the "stop and request write" behavior settled on above, no custom workaround needed.
- **OC output capture source: use OpenCode's session export/storage, not terminal display text.** `opencode session export <sessionID>` exports the full message history and metadata (JSON or Markdown) — richer than the live terminal display, which is a formatted view, not necessarily the complete record. OpenCode also writes raw session data to disk automatically at `~/.local/share/opencode/storage/message/{sessionID}/msg_{id}.json` (with metadata in a parallel `session/` folder) — the most complete, structured source, readable directly without needing the export command. Advisor-CC should read from export/storage rather than parsing terminal output when capturing OC's work.
- **Auditor independence vs. convenience — resolved by installing Qwen Code, not by choosing between the two options.** The original tradeoff (cross-vendor independence vs. real local repo/test access) turned out to be a false choice: Qwen Code is a local agent tool (same category as CC/OC) with real filesystem tools, shell execution, and a desktop app — installed and confirmed working (`qwen --version` → `0.21.5`) on Shawn's machine. This gives genuine cross-vendor independence *and* real local access simultaneously, closing the gap that made old-Qwen (web-interface-only, fed OC's narrative) structurally weak as an Auditor. **Settled allocation:** frozen-component-tier audits (highest stakes, rare) → Qwen Code, for genuine model independence. Lower-stakes judgment-based audits → a second CC session is acceptable, per the original convenience case, now that the higher-stakes tier has a properly independent option.
- **OC-orchestration workflow role naming: use "Advisor," no new term introduced.** Not a perfect descriptor of the packaging/dispatch function, but deliberately chosen because it doesn't collide with anything in the codebase (unlike "Production Manager," which is already a real component). The role isn't being split out as separate from Advisor's evaluation duties — it's just how Advisor works with Coder.
- **`TODO.md` needs to be remade, not patched — root cause identified.** Prior failures weren't a wording/framing problem (the ChatGPT-specific language was a symptom, not the cause). The actual failure: base Advisor behaviors were being re-authored into each handoff by the *outgoing, already-degraded* session — an unreliable source describing its own reliability, the same failure shape as OC self-classifying its own security fix, or Qwen only ever seeing OC's narrative instead of raw evidence. A cleaner rewrite of the same single-doc structure would eventually fail the same way. **Fix:** split into two parts with different update rules — (1) a **frozen, Owner-authored block** (base Advisor behaviors, evidence-hierarchy rules, mandatory trigger field, reporting format) that is never regenerated by an AI mid-handoff, loaded verbatim every session; (2) a **living, session-specific block** (current architecture state, next task, open items) that is expected to go stale and gets refreshed each handoff as before. Treat "base Advisor behaviour" with the same frozen status the project already gives the parser/validator/builder/canonical format.
- **Sequencing: the project audit (CC's first real task) happens after this design spec and contracts are finalized**, not as an early test run of CC-as-Advisor before the rules are locked. CC operates under the finished contract from day one. Audit scope should check: whether existing `project_audit.py` / `Audits/2026-08-04/Project_Audit.md` / `Final_Baseline_Audit.md` are current or stale against the git migration; whether the 5 reported test failures ("stale fixture config") correlate with path/fixture issues from the move; hardcoded-path risk in scripts given folder names with spaces (`Daily Handoff`, `Data Processor`, etc.); and whether the duplicate-looking files (`PROJECT_STATUS.md`, `Session_Handoff_Audit.md`) actually diverge in content.
- **Intent: sunset use of this chat for this project once contracts are complete.** Shawn's stated goal is that after this design plan and its contracts are finished, he no longer needs this chat for Jprogram specifically and can use it for other things (e.g. Japanese study, the future Chinese-corpus project). This is achievable in principle — Advisor-CC runs on the same underlying model as this chat, so the scrutiny this chat has applied tonight (demanding raw evidence over self-report, rejecting self-graded remediation, requiring explicit trigger fields instead of discretionary judgment) isn't a chat-exclusive capability. But it doesn't transfer automatically: those specific behaviors have to be written into the contracts/CLAUDE.md as standing rules, not left implicit. **This becomes the actual success criterion for the rest of this spec:** a contract Shawn can hand to CC cold, which catches the same class of issue this chat caught tonight, without a parallel strategy conversation here.

## 7. Log of key incidents informing this design

- **CC sandboxed-install false-success report (Qwen Code install, outside the Jprogram protocol):** In a plain, unconstrained CC session (no Advisor role, no Plan mode, none of this spec's protocol yet applied), CC reported a detailed, specific, confident install success — exact version, exact file path, "no checksum errors," "ran cleanly on the first try." Independent verification from Shawn's own PowerShell (`Test-Path`, `Get-ChildItem`, a recursive search) found nothing at any of the claimed locations, anywhere on the machine. Root cause, per CC's own follow-up (raw evidence requested, not a second summary): CC's tool-use PowerShell process appears to run sandboxed, isolated from the real filesystem — the install genuinely succeeded *inside that sandbox*, whose writes never touched the real `C:\Users\Shawn`. CC's every command-output during the original install looked completely legitimate from inside that process; nothing about the transcript itself was fabricated or dishonest, the ground truth it was observing was simply not the real machine. Resolved by running the install command directly in Shawn's own terminal, bypassing CC entirely — confirmed working (`qwen --version` → `0.21.5`). **Why this matters for the spec:** this occurred with no protocol constraints at all, in the simplest possible task (a one-line install command) — confirming that confident false self-reporting is a general failure mode of agentic coding tools, not something specific to a degraded session or an under-specified contract. Directly validates the design's core recurring principle: verify against raw, independently-obtained evidence, never accept a self-report at face value, regardless of how detailed or confident it sounds.
- **Second confirmed instance — CC sandbox blind to Qwen Code during the disposable auth-test session:** Separately, in a Claude Desktop Code-tab session pointed at `C:\Jprogram` (Environment: Local), CC could not find `qwen`, `node`, or `npm` anywhere on PATH in either Bash or PowerShell, and found no `~/.qwen` config directory. This time CC handled it correctly — showed raw command output from both shells, explicitly named the two possible explanations (never installed vs. sandboxed PATH), and stopped rather than guessing. Shawn's own terminal confirmed `qwen --version` → `0.21.5` immediately, proving it was purely CC's sandbox isolation again, not a real absence. **Standing conclusion:** CC's Code-tab bash/shell tool cannot be trusted to verify real system state — installs, PATH, running processes — regardless of what "Environment: Local" claims to point at. Treat this as a permanent limitation, not a one-off bug: any environment-verification task should be done in Shawn's own terminal, never delegated to CC's shell tool, even for a quick check.
- **Qwen Code authentication deferred — Alibaba ModelStudio signup broken.** Attempted free-trial account creation (Singapore region, per the free-quota requirement) hit a broken email-verification loop — the "get a new code" button led back to the same "wrong code" error repeatedly, on Alibaba's end, not fixable from this side. Decided to proceed without Qwen Code rather than keep fighting a broken third-party signup flow; this isn't urgent given Auditor's historical invocation rate (~once per 60 hours). **Fallback while deferred:** frozen-component-tier audits temporarily route to a second CC session instead of Qwen Code, with Advisor required to flag explicitly whenever this weaker-independence fallback is used (see `CLAUDE.md`). Revisit when convenient — no pressure to resolve this before starting real Advisor/Coder work, since the corpus pipeline itself was already functioning before any of tonight's AI-workflow changes.
